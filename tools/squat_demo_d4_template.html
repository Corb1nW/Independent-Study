Stage D4: the squat, assembled from the ontology

Through Stage D3 the squat's numbers came from sourced datasets, but its structure was written in Python: the segment chain, the joint signs, which frame belongs to which body, how the upper body and foot were combined, and which coordinate switches a muscle path. In Stage D4 the ontology states that structure. Generic code that names no anatomy reads it, builds the model and runs it. The assembled model reproduces every official D1–D3 result at the stored precision. Anatomy and model check each other on every run, and two hip flexors were added as data alone. Everything below is verified, meaning computed correctly. None of it is yet validated against measured people.

        03 · ASSEMBLY

        How the ontology builds the model

        The executable specification lives in the ontology's models block. It names the segments, the ground segment and its contact points, the modelled joints with their coordinates and location records, the joints merged into segments, and the actuators. The tree is not written down anywhere: it is derived by traversing CONNECTS, REPRESENTED_BY and PART_OF, with the endpoint rule of D-062 Amendment 1.

        The derived tree

        Read left to right from the ground. Each edge is a modelled joint with one coordinate.

        Joints and their conventions

        The new coordinate fields replace D1's hard-coded sign map. Each modelled joint's location comes from a dataset record; the knee's record depends on the variant.

        Endpoint resolution

        How each joint's two segments were found. Joints whose endpoints merge into one segment are locked.

        Body parameters by declared rule

        Three generic rules: direct (a segment's own dataset values), composite (parts merged by locked joints, combined by the parallel-axis theorem) and scaled fraction (de Leva mass fractions, lengths scaled by stature). The specification says which applies to each segment of each body. The lines below are the run's own record of how each segment was built (runs[].how_built).

          04 · ANATOMY ↔ MODEL

          The ontology and the model check each other

          Every assembly runs these checks and writes them into the manifest. ChatGPT's review of the plan (D061-B01) separated topology from leverage: a path can cross a joint with zero moment arm. So crossing (C1) and leverage (C2) are checked independently, and neither reads the other's answer.

          The repair: the knee gap the D3 page found

          The D3 demo showed four thigh muscles acting at the knee in the model with no knee in their ontology entry: the hamstrings and rectus femoris, both sides. Their entries come from hip.yaml, which has no knee to point to, and must keep loading on its own. D4 adds a relationship_additions block in lower_limb_sagittal.yaml. It can only add edges, each with a controlled predicate, existing targets and evidence. With these additions the required-edge check, C1 and the mirror check all pass. Remove them and the required-edge check and C1 fail (test test_a4_on_the_unrepaired_ontology).

          C1 · Crossings by topology

          For each actuator: the modelled joints on the tree path between the segments carrying its path points, against its muscle's declared CROSSES restricted to modelled joints.

          C2 · Leverage by geometry (largest |moment arm|, mm)

          Over the whole motion, all three bodies and both knees, without reading CROSSES. Shaded cells are joints the muscle crosses (C1). A value above 10−9 m outside a crossing would fail. A crossing under 1 mm would be recorded as negligible leverage.

          C3 · Actions and direction

          Structurally, ACTS_ON must be a subset of CROSSES, and every in-plane capability must name a joint in ACTS_ON. For direction, at every pose where a moment arm exceeds numerical zero, its sign must match a declared capability. The one known exception comes from Gait2392 itself, and it is handled against OpenSim, not waved through.

          C4 · Every structural entity traced

          Each joint, coordinate and segment the model uses resolves to dataset records with sources, ontology evidence or a declared convention (D4-B03).

          C5 · Deviation register

          Generated from the ontology into the manifest on every run, not written separately: what is represented, simplified and omitted.

          Deliberate errors the checks must catch (A5)

          Each test changes one thing with all path data fixed, and requires the named check to fail. They are in tests/test_phase_d4.py.

            05 · REGRESSION

            Nothing was lost: every official D1–D3 result reproduced

            Criterion A2 compares the assembled model's output with the official manifests of D1 (dd89fff), D2 (7ac0f2d) and D3 (d3efc56). Every stored series and status is compared at the precision that manifest stores. A stored value with d decimals passes if the new value is within half a unit of the d-th decimal. The excess is how far beyond that half unit the worst value lies: 0 means every number rounds to the stored one. The fixed-knee variant is compared with D1 and D2, and the moving knee with D3. Shapes are checked before values (D4-B01), and the time compared is the time the run emitted.

            06 · VERIFICATION

            The assembled model is computed correctly

            The D1–D3 checks run again on the assembled model (A3), at their written tolerances. These include a second dynamics formulation (Kane's method from generic Jacobians), virtual work, energy, Newton's law and forward integration. Geometry and kinematics are compared with OpenSim 4.6 references regenerated by the verification job. The table shows the worst case over all six runs: three bodies, fixed and moving knee.

            Muscle feasibility, as in D2 and D3

            Feasible: the muscles supply every torque without reserve beyond 1 N·m. The fixed knee's shortfall for two bodies is D2's known result, reproduced. It is not a D4 regression.

            07 · GROWTH TEST

            Two muscles added as data, with no code change

            Claim B's strongest test is to add anatomy the old code could not handle. Gait2392's iliacus and psoas each have a path point switched by the hip angle. D1–D3 could only switch points by the knee angle. Their anatomy was already in hip.yaml with evidence. Commit 7c57224 added two actuator entities, a specification that extends squat_d4, regenerated dataset records, OpenSim references and a run configuration. No file in src/ or tools/ changed (A7).

                10 · WHAT IT MOVES FORWARD

                How D4 serves the proof of concept

                Corbin's goal for this phase (Q65) is to prove two things: that working with AI can produce legitimate scientific research, and that an ontology of the musculoskeletal system can build a digital twin. The plan (D-061) breaks each into concrete properties. D4 was scoped to show Claim B's first three. It also added to Claim A, because its acceptance criteria and a hypothesis were written down before any result existed.

                CLAIM B

                An ontology of the musculoskeletal system can build a digital twin

                  CLAIM A

                  Working with AI can produce legitimate scientific research

                    What the next stage inherits

                    Before D4, every new muscle meant new code paths and new hard-coded tables. Now a muscle enters through the same route the growth test used: an actuator entity linked to its anatomy, dataset records, a line in a specification, and an OpenSim reference. The checks then tell us at once whether anatomy and model agree. D5 would add the rest of Gait2392's leg muscles this way, about 27 more, and test passive force and compliant tendons. The near-standing co-activation that D-061 planned to test in D5 was already tested by D4's H1. Where the project goes next is Corbin's decision (Q67).
