**Context.** Each handoff currently means downloading a repository zip, uploading it to the other model, and recreating files from chat output. This is slow, and it risks errors: a file transcribed or regenerated by hand may differ from what was reviewed. Corbin proposed giving both models direct access to the project files.

**Decision.**
1. **Canonical remote.** A private GitHub repository is the single shared copy of the project, holding the full history from baseline `d04fb78` onward. Local folders, including Corbin's, are working clones.
2. **`main` is owner-controlled.** Only Corbin merges into `main`. Models never push to `main`.
3. **Builders work on branches.** Branch names follow `<phase>/<model>-<topic>` (e.g. `phase-b/claude-hip-model`). When work is ready, the builder opens a pull request. The PR description is the D-048 handoff: starting snapshot, changes, validation commands and results, proposals and open questions.
4. **Reviewers review a commit.** The reviewer checks out the PR's head commit and states its hash in the review. Executable claims are reproduced against that commit (D-045). Findings go in the PR review. A substantial review is also committed to `docs/reviews/`.
5. **Approvals live on the PR.** Corbin's approving review or merge on a PR is a valid approval basis under D-042. It is recorded in `DECISIONS.md` §4 with the PR link and Corbin's comment, quoted verbatim.
6. **Only committed states count as snapshots.** A model may work directly in a local clone, for example Claude through the desktop app link. Findings, however, always cite a pushed commit. Uncommitted or unpushed files are never a reviewed snapshot (D-046).
7. **Scoped access.** Each model's access is limited to this repository. Credentials and tokens are never pasted into chat.
8. **Fallback.** If a model cannot reach the remote, the current method (a zip with git history, plus the commit hash) remains valid. The handoff states which method was used.
9. **Optional, proposed separately: CI.** A GitHub Actions workflow could run `pytest`, `python -m src.integrity` and `tools/review_cycle1_probes.py` on every PR. CI results would be supporting evidence only. They would not replace the reviewer's reproduction under D-045, and they would not change verification-status semantics. If wanted, this would be filed as its own decision.

**Defense.**
- **Removes the transfer step.** Both models read the same files directly, with no download, upload or recreation in between.
- **Makes snapshots automatic.** Every handoff points to a commit, which is what D-046 and D-048 already require.
- **Keeps review honest.** A PR diff shows exactly what changed. Reviewing a fixed commit rules out the case where files change between a test run and the report.
- **Makes approvals traceable.** A PR approval is a durable, linkable record. That satisfies D-042 better than quoting chat messages.
- **Preserves owner control.** Protecting `main` enforces D-047's line in software as well as by convention: models build and propose; Corbin decides.

**Alternatives.**
- *(a) Both models work directly in one shared local folder* (Corbin's original idea, taken literally). Rejected as the primary mechanism, for three reasons. First, there is no fixed snapshot: files can change mid-review. Second, simultaneous edits can overwrite each other silently. Third, it depends on each model having a live link to Corbin's computer. It is kept as a permitted way of *working* (item 6), but not as the handoff.
- *(b) Shared cloud folder (Drive, Dropbox).* Rejected. It has the same snapshot problem as (a), and git history is lost or awkward to keep.
- *(c) Status quo (zip uploads).* Rejected as the default because of its time cost and transcription risk. It is kept as the fallback (item 8).

**Challenges.** None yet. ChatGPT's review is pending.

**Consequences.**
- The project depends on a GitHub account and on each model's GitHub access.
- Branch protection on a private repository may require a paid GitHub plan. GitHub Pro is available free through the GitHub Student Developer Pack; check current terms. Without protection, item 2 is a convention only.
- The PR becomes the unit of handoff, so `PROJECT_STATE.md`'s snapshot line should reference the remote and the latest merged commit.

**Questions for ChatGPT.**

2. Can you open branches and pull requests, or only read? If you can only read, should you file reviews as committed files, or should Corbin paste them as PR comments?
3. Any amendments to items 1–8? Is item 9 (CI) worth a separate proposal now, or after Phase B?

## Part 2: Setup checklist (for Corbin, after approval)

1. **Create the repository.** On GitHub, create a new **private** repository (e.g. `lb-ao`). Do *not* initialize it with a README or `.gitignore`, so it starts empty.
2. **Push the existing history.** In your local copy of the project (the one containing `d04fb78` and `4abb4f1`):
   ```bash
   git remote add origin https://github.com/<your-username>/lb-ao.git
   git push -u origin main
   git tag baseline d04fb78
   git tag phase-a-built 4abb4f1
   git push origin --tags
   ```
   Then confirm on GitHub that both commits appear in the history.
3. **Protect `main`.** In Settings → Branches (or Rules), require a pull request before merging, and allow only yourself to merge. If the option is unavailable on your plan, see Consequences above.
4. **Connect Claude.** Link GitHub to claude.ai in Settings → Connectors. In a session, I can then attach the repo directly.
5. **Connect ChatGPT.** Use ChatGPT's GitHub integration and grant access to this repository only. Its answers to the questions above determine what it can do.
6. **First use.** Ask ChatGPT to run its Phase A review against `phase-a-built` (`4abb4f1`) from the remote, in place of the zip.
7. **Record the decision.** Once you approve, the next build commit adds D-051 to `DECISIONS.md` (with your approval quoted in §4) and updates the snapshot line in `PROJECT_STATE.md`.
